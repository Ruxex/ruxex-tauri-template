# ARIA Label Accessibility Design

## Intent

Ruxexの実Tauri UIをWebdriverIOの逐次セッションから安定して観測・操作できるようにする。対象はまずアクセシブルネームの不足であり、既存画面の見た目、DOM構造、ルーティング、イベント処理、プロバイダ通信は変更しない。

## Goals

- 本番コードの`button`、`input`、`select`、`textarea`に、ARIAラベルを明示する。
- ラベルは画面上の既存の意味と一致させ、動的な対象名や状態を含める。
- WebdriverIOのsnapshot/find/click/fillから、主要なログイン、ナビゲーション、チャット、プロジェクト、設定、承認操作を名前で特定できるようにする。
- 将来のUI変更でラベルが抜けることを静的テストで検出する。

## Non-goals

- HTMLセマンティクス、DOM階層、CSS、表示文言、キーボード操作、フォーカス管理の再設計。
- `role`、`tabIndex`、`data-testid`、テスト専用属性の追加。
- ARIAライブリージョン、スクリーンリーダー向けの読み上げ順、色コントラスト、視覚的なアクセシビリティ全般。
- 実プロバイダへのログインやAPIリクエスト。

## Constraints

- 既存の`aria-label`は維持し、意味を変えない。
- 新しいラベルは英語の既存UI文言に合わせ、アイコンだけの操作には動詞を含める。
- プロジェクト名、チャット名、プラグイン名、選択状態など、対象を区別する必要がある場合は動的値をラベルに含める。
- 本番の通常Tauri capabilityにテスト権限や診断プラグインを追加しない。

## Approach

本番TSXを静的に走査し、`button`、`input`、`select`、`textarea`の開始タグに`aria-label`があることを契約化する。対象コンポーネントへラベルだけを追加し、既存テストを維持する。実装後はフロントエンドテスト、静的契約、ビルド、必要に応じて一時ホームのdummy providerを使った実Tauri逐次セッションで確認する。

## Acceptance criteria

- 本番TSXの対象操作要素にARIAラベルがある。
- 静的アクセシビリティテストが成功する。
- 既存のフロントエンドテスト、Pythonテスト、ビルドが成功する。
- 実Tauriセッションでスナップショットからラベル付き入力とボタンを見つけ、再起動なしに操作できる。
- 差分に表示・挙動・プロバイダ通信の変更がない。
