# 適用・レビュー・ガイドの運用

この文書はガイドを保守し、後続の実装へ安全に引き継ぐ方法を定めます。**この段階では既存UIへの反映、テーマ値の変更、コンポーネントの改修、トークン導入を行いません。** ここで定めるのは後続作業の進め方です。

## 5段階の成熟プロセス

| 段階 | 成果 | 完了の目安 |
| --- | --- | --- |
| 1. 哲学 | 何を優先する製品か、判断が衝突したときの順序 | 製品境界、アクセシビリティ、情報構造、既存パターンの優先関係が説明されている |
| 2. 視覚基盤 | レイアウト、余白、部品寸法、色、文字 | ページと部品の判断に役割別の基準があり、値の根拠と例外が分かる |
| 3. コンポーネントと状態 | 操作、フォーム、選択、ダイアログ、非同期状態 | 各パターンで意味、状態、入力、フォーカスの扱いが説明されている |
| 4. 参照例 | ページ・フォーム・状態・確認操作のコード例 | 例が基礎ガイドと一致し、実装時に判断の出発点として使える |
| 5. 運用ガイド | レビュー、例外、段階導入、改訂の手順 | チームがガイドを使い、根拠を記録し、実装へ移す判断ができる |

段階5の完了はガイド群の初版完成を指します。共通CSSトークン、共通Reactコンポーネント、Ladleカタログ、既存画面への一括適用が完了したことを意味しません。

## 新しい画面・変更をレビューする順序

1. **製品上の事実を確認する。** App Serverや既存の製品契約が決める状態・操作を見た目の都合で変えません。
2. **画面の主目的を決める。** 主な対象、主要操作、補助情報を決め、画面骨格と幅を選びます。
3. **グルーピングを決める。** 余白、面、境界の担当を分け、同じ間隔を二重に作りません。
4. **部品と状態を選ぶ。** 既存コンポーネントを確認し、通常、選択、ホバー、フォーカス、無効、読み込み、エラー、空の状態を整理します。
5. **可変条件で確認する。** 最小幅、ペインの開閉、長い名前・パス・翻訳文、文字サイズ変更、ズーム、キーボード操作を確認します。
6. **テーマを確認する。** ライト／ダークとサポートするプリセットの状態を見て、色の役割とコントラストを確認します。
7. **再利用可能な差分だけを共有化する。** 同じ役割で繰り返すルールが確認できた場合に、トークンや共通部品の候補にします。

## 例外の記録

ガイドから外すときは、変更理由、該当する画面・部品、影響する状態、他の選択肢を避けた理由、再確認する条件を短く記録します。例外は製品データ、キーボード・支援技術での操作、テーマ対応を損なってはいけません。

バッジ内と選択済みスキルの解除ボタン、および高頻度作業面としてのチャットComposerは、[部品の内側余白と操作サイズ](./03-component-spacing.md)に定義済みの寸法例外です。ほかの小さい操作へ自動的に例外を広げません。例外が同じ役割の複数画面へ広がった場合、局所クラスを追加し続けず、基礎ルールまたは共通パターンの不足として見直します。

## 実装へ進む前の準備

各後続実装は、対象範囲を小さく分け、代表的な画面・部品で検証します。少なくとも次を決めてから実装計画を作ります。

- 代表画面と対象コンポーネント、および明確な対象外。
- 使う既存DaisyUI／Tailwindユーティリティと変更候補の理由。
- ライト／ダーク、フォント設定、ユーザーズームでの受け入れ条件。
- キーボード、フォーカス、支援技術、可変コンテンツの受け入れ条件。
- 新たなトークンや共通コンポーネントを追加する必要性と移行方法。
- 既存画面を一斉変更せず、どの順で適用・確認するか。

まず代表ページでガイドが自然に使えるか確かめ、複数の異なる画面でも再利用できると分かった値や部品から共有化します。単独画面の都合を全製品のトークンにしません。

## このガイド群の改訂

- 変更は具体的な画面・状態・ユーザー影響の例を根拠にします。「好み」だけで数値や例外を追加しません。
- 同じ判断は一つの基礎ガイドで定義し、ほかの文書は参照します。矛盾を見つけた場合は、複数箇所を個別修正する前に正本を決めます。
- DaisyUI、Tailwind、ブラウザー要件、ユーザー設定の仕様が変わった場合、関連する値、参照例、検証方法を一緒に見直します。
- 実装に進んだ後は、ガイドと実際の共通部品が一致しているかを定期的に確認します。意図的な差異はこの文書の例外として説明します。
- 各変更では対象文書、依存するルール、未検証のテーマ・画面範囲をレビューで明示します。
