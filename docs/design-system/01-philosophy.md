# Ruxex デザイン哲学

この哲学は、Ruxexの各画面を同じ見た目にするためではなく、異なる画面でも一貫した判断ができるようにするためのものです。画面の形が違っても、作業の流れ、情報の優先順位、操作の手応えが同じ製品として感じられることを目指します。

## Ruxexが支える仕事

Ruxexは、App Serverを通じてエージェントと協働するデスクトップワークベンチで、ローカル実行を基本とします。Projectは作業の文脈、Threadは進行中のやりとり、Composerは次の依頼を形にする場所です。画面は機能の一覧を並べるより、いま取り組んでいる対象と次に必要な操作を見つけやすくします。

RuxexのUIには、ワークベンチ、Project、Thread、Composerで培われた既存の操作パターンがあります。新しい画面はこの語彙を尊重し、独立した小さな製品のような見た目や振る舞いを持ち込まないようにします。

## 原則

### 1. 作業対象を中心に置く

各画面では、ユーザーが確認・編集・判断している対象を最も見つけやすい位置に置きます。主要な内容と主要な操作を近づけ、補助情報は視線を奪わない位置に置きます。ページ、一覧、会話、設定では最適な密度が異なるため、同じレイアウトを強制せず、同じ優先順位の考え方を共有します。

### 2. 画面は実際の状態を正確に表す

Thread、Project、承認、モデル選択、実行状態など、App Serverが管理する情報はそのプロトコルを基準にします。UI都合で状態を推測したり、存在しない状態を作ったりしません。ローカルに保存するUI状態は、テーマ、密度、パネル表示などのプレゼンテーション設定に限ります。

視覚的な強調は、状態や重要度の実態と一致させます。色、配置、アイコン、ラベルは同じ意味を支え、色だけに意味を担わせません。

### 3. 余白と整列で構造を伝える

まず余白と共通の揃え位置でグループを伝えます。背景面はまとまりや選択状態を示す必要があるときに使い、区切り線は情報密度が高く余白だけでは読み分けにくいときに使います。

同じ列や階層では端を揃えます。内側の間隔とグループ間の間隔に差をつけ、ひとまとまりの情報と別の情報が混ざって見えないようにします。

### 4. 適切な密度を選ぶ

Ruxexは長時間使う作業環境です。一覧や状態表示は素早く走査できる密度を保ち、重要なページ区切りや読み込む内容には十分な空間を与えます。全てを広く、または全てを詰めて配置するのではなく、役割ごとに密度を定めます。

### 5. 一貫性を保ち、必要な違いは残す

同じ役割のページコンテナ、セクション、一覧行、操作群には同じパターンを使います。会話、テーブル、ナビゲーションのように目的が違う領域は、それぞれの読みやすさと作業効率に合う形を保ちます。見た目が似ているだけの要素を無理に一つのコンポーネントへまとめません。

### 6. コンテンツの成長と画面の変化に耐える

Thread名、パス、翻訳後のラベル、エラー文は長さが一定ではありません。固定幅や固定高で内容を切り捨てず、折り返し、縮小、スクロールを役割に応じて選びます。ウィンドウやペインの幅が変わったときは、内容が収まらなくなった地点で配置を切り替えます。

### 7. 説明を増やす前に、見た目と操作を明確にする

階層、グルーピング、アイコン、状態、操作の形で意味が伝わるなら、説明文や補助文を重ねません。文言は名前、操作、状態、エラー、必要な空状態の案内に絞り、短く具体的にします。アイコンだけの操作にもアクセシブルな名前を付けます。

## 判断の優先順位

複数の案が成立するときは、次の順で判断します。

1. プロトコルと製品境界に忠実であること。
2. キーボード、支援技術、ズーム、可変コンテンツで操作できること。
3. 情報の順序とグルーピングが明確であること。
4. 既存の共通パターンとトークンを再利用できること。
5. 見た目の好みや装飾を調整すること。

## 適用と例外

この哲学は、実装ガイドとコンポーネント仕様の土台です。個々の画面に適用するときは、例外の目的を先に言語化し、同じ制約を持つ画面にも再利用できる形にします。例外が複数画面に広がった場合は、哲学かガイドの不足として見直します。

現行の製品制約については [`ruxex-tauri-template/AGENTS.md`](../../AGENTS.md) を、既存画面の決定については [`ruxex-gui-foundation-1-4.md`](../ruxex-gui-foundation-1-4.md) と [`ruxex-product-direction-memo.md`](../ruxex-product-direction-memo.md) を参照します。これらの製品境界や実装上の要件を、見た目の統一より優先します。
