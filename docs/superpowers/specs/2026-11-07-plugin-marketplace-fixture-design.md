# Plugin Marketplace Fixture Design

## Intent

Extend the UI fixture workflow with marketplace and plugin states using the
real local `openai-plugins` checkout. The fixture must exercise the same
App Server marketplace/add and plugin/install flows as a user, while keeping
the generated home out of Git and avoiding machine-specific absolute paths in
the WDIO source.

## Goals

- Use the real marketplace manifests, plugin manifests, Skills, and MCP
  metadata from the sibling `openai-plugins` checkout.
- Create marketplace and installed-plugin state through the desktop UI and
  App Server protocol, never by editing config or plugin-store files directly.
- Store only a repository-relative source path in the fixture code.
- Resolve that path to an absolute path at runtime before entering it into the
  marketplace form.
- Keep the scenario idempotent by rebuilding the ignored fixture home before
  the persistent marketplace run.
- Cover empty, configured, uninstalled, and installed plugin screens.

## Non-goals

- Copying the marketplace checkout into `ruxex-tauri-template`.
- Committing generated marketplace checkouts, installed plugins, screenshots,
  or the generated fixture home.
- Testing plugin runtime authentication or invoking third-party services.
- Depending on a live model provider; plugin installation is a local App Server
  operation for this fixture.

## Source resolution

The source is represented as a path relative to the template repository:

```text
../../openai-plugins
```

The WDIO support module resolves it with `path.resolve(repositoryRoot, source)`
and verifies that the result is a directory before navigating to the
marketplace settings page. The resolved absolute path is only runtime input;
it is not written into tracked source files.

The path is passed to the App Server through the normal `marketplace/add`
request generated by the settings UI. App Server treats a local directory as a
local marketplace root and records its source in the generated home. When a
plugin is installed, the normal plugin store installation copies the plugin
into the home, matching real application behavior.

## Scenario model

The persistent marketplace suite starts from a clean ignored home and performs
these operations through WDIO:

1. Verify the empty marketplace state on `/capabilities`.
2. Open `/settings/marketplaces` and add the resolved local marketplace path.
3. Verify the actual `openai-curated` marketplace and its categorized plugin
   list.
4. Open an actual plugin detail page while it is not installed.
5. Install one actual plugin through its UI card.
6. Verify the installed state on the capabilities page and in the sidebar.
7. Open the installed plugin detail page and verify its installed controls and
   metadata.
8. Leave at least one other actual plugin uninstalled so both states coexist.

The initial plugin choices should be selected from the checked-out manifests
at runtime or declared as stable plugin names whose manifests are present in
the checkout. The first implementation should prefer plugins with local
metadata and no required runtime authentication for the screenshot itself.

## Idempotence

- The marketplace fixture runner removes and recreates only its ignored home.
- Adding the marketplace to a fresh home is always performed through the UI.
- The scenario must assert the marketplace name and selected plugin names so a
  missing or incompatible checkout fails clearly.
- Re-running against a changed checkout is allowed to update visual content,
  but the runner must fail with a useful message if the selected plugin no
  longer exists.

## Verification

Run the focused WDIO marketplace fixture in headful mode, then verify:

- the empty marketplace state is visible before addition;
- the actual marketplace list loads after addition;
- the selected plugin detail page is reachable before installation;
- installation changes the UI to installed state;
- the sidebar exposes the installed plugin;
- the generated home remains ignored and no screenshots are tracked.

Also run the existing Python, frontend, formatting, and diff checks before
committing.
